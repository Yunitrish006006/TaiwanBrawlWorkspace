# 情侶天數元件計劃書（草案）

狀態：CD-00 至 CD-03 已完成設計或本機實作，含資料庫、後端 API、社交與帳號停用整合；尚未正式啟用，前端與桌面元件待做

版本：v0.4（搭配 [Luna 執行任務書](couple-days-implementation-taskbook.md)）

本版目的：固定產品語意與第一版邊界，依任務書逐切片實作。目前已有後端 schema、交易及受開關保護的 API 與本機驗證；前端、真機及正式部署未完成，不能視為整體功能完成。

## 0. 先討論的產品結論

使用者已確認：自選第一天、單方解除立即生效、每人最多一位情侶、修改日期需另一方同意、封鎖／刪好友前提醒並同時解除、好友列表與詳細頁僅雙方可見。另外要求 Android 與 iPhone 都提供手機桌面元件顯示天數。

補充已確認：初次邀請須接受；依各自所在地日期計算；只選今天或過去；桌面顯示伴侶名稱與天數（後續已確認）；離線持續計算、App 開啟也同步；邀請與日期提案 7 天失效、不設拒絕後 24 小時冷卻。刷新頻率由工程評估。

以下整理產品方向；資料保留及第二階段範圍仍屬工程建議：

- 情侶關係只能從既有好友建立，且必須雙方同意。
- 一個使用者第一版最多一個 `active` 情侶關係。
- 使用者可以自行選定交往起始日，該日期就是「第一天」；交往日期使用自然日而不是時間戳。
- 起始日與關係由伺服器保存；裝置按所在地曆日計算天數，資料庫不每日累加。
- 解除情侶關係由任一方操作後立即生效，雙方都停止看到目前天數；解除歷史先保留在後端，但第一版不做公開歷史頁。
- 狀態預設只對情侶雙方可見，不出現在公開搜尋、排行榜或其他好友的畫面。
- 第一版限制每個使用者最多一個 `active` 情侶關係；顯示在好友卡片、詳細頁及 Android／iPhone 桌面元件，不先做週年提醒、公開動態、照片牆或情侶專屬主題。

不得將上述工程建議全部視為使用者已確認。正式實作前依任務書固定契約與建議預設。

## 0.1 MVP 使用者故事

1. 我可以在好友列表選擇一位好友，送出包含交往日期的情侶邀請。
2. 對方可以接受或拒絕；未接受前不能顯示為正在交往。
3. 接受後兩邊使用相同起始日，依各自所在地顯示「交往第 N 天」；當地日期不同時天數可不同。
4. 我重新登入、清除快取或跨裝置登入後，仍可取得正確狀態。
5. 任一方解除後，雙方都不再看到目前交往天數，且舊邀請不能把關係重新啟用。

## 0.2 明確不納入 MVP

- 依 GPS、照片、興趣或推薦演算法自動配對。
- 公開情侶狀態、好友排行、社群貼文或其他人可見的紀念日。
- 週年推播、生日提醒、情侶任務、情侶徽章與專屬聊天主題。
- 任意時間精度、跨時區逐小時計算、每日寫入計數器。
- 直接修改資料庫或由前端自行宣稱 `active`。

## 1. 功能目標

在好友列表中，讓兩位已建立好友關係的使用者可以互相綁定為「情侶」，設定交往起始日，並在好友列表或好友詳細資訊中顯示目前交往天數。

第一版的核心不是社交配對，而是「雙方同意後，保存一筆有權限限制的情侶關係與起始日」。天數由起始日與目前日期計算，不直接保存每天累加的數字。

## 2. 建議的第一版範圍

### 2.1 使用者流程

1. 使用者在好友列表選擇一位好友。
2. 點擊「綁定為情侶」並送出邀請。
3. 對方在好友列表或通知中看到情侶邀請。
4. 對方接受後，雙方建立同一筆情侶關係。
5. 任一方可以查看交往起始日與目前交往天數。
6. 任一方確認解除後立即生效，不需另一方批准。
7. 任一方提出新日期，另一方同意後才變更；等待期間維持原日期。
8. 封鎖或刪除情侶好友前提醒，操作完成時同時解除綁定。
9. 使用者可自行加入手機桌面元件，查看交往天數。

### 2.2 顯示位置

已確認第一版 App 內有兩個位置，僅雙方可見；另增加手機桌面元件：

- 好友列表：在已綁定情侶的好友卡片顯示「交往第 N 天」。
- 好友詳細資訊：顯示起始日、天數、關係狀態與解除操作。

暫不包含首頁大型紀念日卡片、排行榜、公開動態、照片牆、週年提醒或情侶專屬聊天主題。

### 2.3 起始日規則

交往開始日期保存為相同的 YYYY-MM-DD，不轉換成時間戳。今天依觀看裝置目前所在地的系統時區決定，不需 GPS；時區改變立即重算，因此跨時區兩人可有不同天數。

初版建議：

- 起始日不可晚於今天。
- 建議輸入下限為 1900-01-01，上限為操作者所在地今天；後端以 serverNow 與有效 IANA 時區驗證日期，不相信客戶端傳入的今天。接受時也驗證接受者當地日期，若仍是未來則提示待當地進入該日再接受。
- 顯示天數採包含起始日的自然日計算，起始日當天顯示第 1 天。
- 不讓前端直接傳入或修改累計天數。

## 3. 關係與權限模型

### 3.1 狀態

建議關係狀態如下：

| 狀態 | 意義 |
| --- | --- |
| `pending` | 一方送出邀請，等待對方決定 |
| `active` | 雙方已同意，正在交往計算 |
| `declined` | 邀請被拒絕 |
| `ended` | 已解除情侶綁定 |
| `cancelled` | 邀請在接受前被撤回 |

### 3.2 權限原則

- 只有雙方已存在的好友關係可以發出情侶邀請。
- 情侶綁定必須由雙方明確同意，不能由單方直接改成 `active`。
- 初始日期建議隨邀請固定，接受者確認或拒絕；綁定後任一方可提修改，另一方接受後生效。
- 伺服器是關係狀態與起始日的權威來源。
- 前端只能顯示伺服器回傳的狀態，不能以本地資料自行宣稱已綁定。
- 封鎖與解除好友同時解除情侶；帳號停用／刪除的失效處理須在後端整合。

## 4. 建議資料模型

最新確認：情侶併入獨立社交資料庫 SOCIAL_DB，與好友、封鎖及聊天共庫；帳號／登入仍在主庫 DB，遊戲使用 GAME_DB。此決策取代情侶獨立庫方案，詳見 [資料庫拆分計劃](database-separation-plan.md)。刪好友／封鎖與解除情侶採社交庫內原子操作，帳號停用／刪除另處理跨庫同步。

建議新增獨立的 `couple_relationships` 與 `couple_requests`，不要把情侶欄位直接塞進既有 `friendships`，以免好友關係與情侶關係的生命週期互相污染。

### 4.1 `couple_relationships`

- `id`
- `user_a_id`、`user_b_id`：以較小 user ID 放在 `user_a_id`，避免同一對使用者重複建立
- `started_on`：交往起始日
- `status`
- `created_at`、`updated_at`
- `ended_at`：解除後保存歷史，不刪除關係
- `ended_by_user_id`：記錄解除者；是否對外顯示待決定

成對唯一不夠保證每人一位情侶。建議另設 couple_active_members，以 user_id 主鍵佔用每位使用者；使用已驗證的 D1 原子操作一起建立雙方成員、關係並消耗邀請。歷史關係不得阻擋同一對重新綁定；詳細競態要求見任務書。

### 4.2 `couple_requests`

- `id`
- `relationship_id` 或候選雙方 user ID
- `requester_id`
- `recipient_id`
- `proposed_started_on`
- `status`
- `created_at`、`responded_at`

同一對使用者同時間只允許一筆有效邀請。重複送出應回傳既有狀態，而不是建立多筆邀請。

## 5. 建議 API 方向

實際路徑需配合既有 backend route 風格確認，先列出語意而不鎖定最終命名：

- `GET /api/couples/overview`：取得目前使用者的情侶關係與待處理邀請摘要
- `POST /api/couples/requests`：對好友送出邀請，內容包含 `targetUserId`、`startedOn`、`timeZone` 與 `operationId`
- `POST /api/couples/requests/:id/accept`：接受邀請與所附起始日
- `POST /api/couples/requests/:id/reject`：拒絕邀請
- `POST /api/couples/requests/:id/cancel`：撤回尚未接受的邀請
- `POST /api/couples/:relationshipId/end`：解除情侶關係
- `POST /api/couples/:relationshipId/date-proposals`：提出新日期與預期版本
- `POST /api/couples/date-proposals/:id/accept`、`reject`、`cancel`：由對方接受／拒絕，或發起者撤回

回應包含對方基本資料、關係狀態、startedOn、serverNow、version／更新時間；dayCount 由每台裝置依當地日期計算，不提供全關係共用的權威天數。詳細同步規則見任務書。

## 6. 前端元件方向

建議抽成可重用的 `CoupleDaysBadge` 或同等名稱元件：

- `status == active` 才顯示天數。
- `pending` 顯示「等待確認」或「有新的情侶邀請」。
- `ended` 不顯示目前天數；建議第一版不提供歷史頁。
- 無資料、載入中、錯誤與離線狀態要有獨立呈現，不使用假的天數。
- 元件只接收明確的 view model，不直接呼叫 API 或操作 Hive。
- 本地快取只能用於離線顯示上次已確認資料，重新連線後必須以伺服器狀態更新。

## 7. 隱私與濫用防護

- 情侶狀態預設只對雙方可見，不加入公開好友搜尋結果。
- 解除在伺服器立即生效；另一方同步後清除天數。離線依上次 active 狀態持續計算，不設 24 小時截止；App 詳細頁保留最後同步資訊，桌面顯示伴侶名稱與天數（後續已確認）。不承諾即時遠端清除。
- 不在推播標題或鎖定畫面直接顯示敏感的情侶內容，除非產品明確選擇。
- 需要防止邀請轟炸、重複邀請與已封鎖使用者操作。
- API 必須以登入身分驗證與好友關係做授權，不能只相信 `friendId` 或 `relationshipId`。
- 記錄必要的建立、接受、拒絕與解除 audit 資訊，但不保存多餘的私人內容。

## 8. 分階段實作建議

### Phase 0：產品決策與契約草案（依第 10 節確認紀錄）

- 固定邀請、日期修改、時區、資料保留與手機平台規格。
- 已確認的第一天、單方解除及每人一位限制不再視為未回答。

### Phase 1：後端資料與權限

- migration、狀態機與唯一性約束。
- 情侶邀請與接受／拒絕／撤回／解除 API。
- 好友、封鎖、登入 session 與帳號狀態授權測試。
- 不涉及前端畫面的 route regression 與 migration rehearsal。

### Phase 2：前端好友列表整合

- friends model／remote source／service 擴充。
- 好友卡片的情侶狀態與天數元件。
- 邀請、接受、拒絕與解除操作。
- loading、error、offline 與 stale cache 行為。

### Phase 3：跨 repo 驗證與可選通知

- 前後端 contract snapshot 與 test matrix 更新。
- 雙帳號端到端流程：邀請、接受、顯示、重新登入、解除。
- 若決定加入通知，再另立 notification slice，不把通知當成關係資料來源。

## 9. 驗收條件草案

- 非好友不能送出情侶邀請。
- 同一對使用者不能同時存在兩筆 active 關係。
- 雙方未接受前，任何一方都不能看到 active 天數。
- 接受後起始日相同；當地日期相同則天數相同，不同則按各自日期驗收。
- 日期跨日後，天數能依規則正確增加，不需每日寫入資料庫。
- 重新登入、清除前端快取後，仍能從伺服器恢復正確狀態。
- 解除後不再顯示目前天數，且舊邀請不能再次使關係變成 active。
- 封鎖、解除好友、重複點擊、重送請求與網路錯誤都有明確結果。
- 前端 analyzer／tests、後端 tests、workspace contract validation 全部通過。
